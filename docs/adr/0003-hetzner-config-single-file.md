# The Hetzner fleet and software registry share one config file

`~/.config/hetzner/fleet.json` (server connection metadata, written by `hetzner-create`, pruned by `hetzner-delete`, read by `hetzner-ssh`) and `~/.config/hetzner/software.json` (self-hosted app version pins and upgrade commands, read and written by `hetzner-update`) were two files describing one machine's relationship to one Hetzner account. Nothing enforced which one held what, the two schemas were documented in READMEs in two different repos, and `hetzner-update/README.md` claimed both were "machine-local and not synced" while chezmoi tracked both — a doc that had already drifted from the truth. They are merged into a single `~/.config/hetzner/hetzner.json` with two top-level sections, `fleet` and `software`, so there is one file to find, one file to vault, and one place a stale claim can be corrected. `software.<app>.server` continues to reference `fleet.servers.<name>` by key, so an app can still move between boxes by editing one string. Vocabulary is fixed in [CONTEXT.md](../../CONTEXT.md): **Fleet** (not roster), **Software registry**, **Hetzner config**.

## Considered Options

- **Nest each app under the server it runs on** (rejected) — removes the name-based cross-reference, but `/hetzner-update multica` then has to scan every server to find one app, and moving an app between boxes becomes a subtree move instead of a string edit.
- **Rename to `hetzner.json` with `fleet{}` + `software{}` sections** (chosen) — costs a rewrite of every `~/.config/hetzner/fleet.json` string across five skills in two repos, plus one extra level on every JSON pointer (`servers.main.ip` → `fleet.servers.main.ip`), but the filename stops lying about holding only the fleet.
- **Keep the `fleet.json` filename and bolt `software{}` onto it** (rejected) — smallest possible diff, but leaves a file named after one of the two things it contains, which is the confusion this change exists to remove.
- **Fallback reads (try `hetzner.json`, fall back to the old pair)** (rejected) — every reader would carry a permanent two-path branch, reintroducing the "which file is authoritative?" question in code instead of on disk. A dated note to remove the fallback later is a note nobody acts on.
- **Ship a JSON Schema and validate on load** (deferred) — the referential rule that actually bites (`software.<app>.server` must resolve to a real `fleet.servers` key) is not expressible in JSON Schema without `$data`, so a hand-rolled check is needed regardless; and Homebrew's Python is PEP 668 `EXTERNALLY-MANAGED`, so `jsonschema` would arrive via a PEP 723 / `uv run` header that turns a zero-dependency script into a `uv`-dependent one. Not worth it for one author on one machine, where a broken reference surfaces the first time a skill runs.

## Consequences

The cutover is a hard cut with no compatibility window: readers ship first (`ai`, then `ai-agent`), the config flips last, and `/plugin update` is required afterwards because the installed skills live in a downstream clone of this repo at `~/.claude/plugins/marketplaces/marketonfire`. Between writing the new config and running `/plugin update` the installed skills read a path that no longer exists — a window one command wide, accepted because the fleet is one machine.

Schema ownership and schema documentation deliberately sit apart. This repo owns the shape (`hetzner-create` writes the file and ships the example); `ai-agent` consumes it via `hetzner-update/scripts/read-state.py`, whose two path overrides collapse into one `HETZNER_CONFIG_JSON`. Nothing mechanical stops a shape change here from breaking that reader — accepted, and recorded so the next person knows which side gets to move first. Each README continues to document only its own section, so the top-level envelope is named in both rather than described in full by either.

`.chezmoiremove` is deliberately not used to retire the old files: this Mac is the only machine that has ever applied them, so the migration `rm`s them directly. Note that dropping a file from a chezmoi source tree does not delete it from `$HOME` — without that explicit `rm`, `fleet.json` would linger looking authoritative while nothing read it.

## Deferred

- **Prose still says "roster".** `CONTEXT.md` marks the word `_Avoid_` in favour of **Fleet**, but the migration only rewrote lines it was already touching for the path change. `hetzner-ssh/SKILL.md` still has "Step 0 — Load the roster", and `hetzner-delete/SKILL.md` still says "Re-render from the updated roster". A prose sweep is a separate, low-risk pass.
- **`hetzner-update` lives in `ai-agent`, the schema lives in `ai`.** Nothing mechanical stops a shape change in `ai` from breaking `read-state.py`. Moving the skill into `ai` would close it, but `software.multica.remote.upgrade_cmd` hard-codes an absolute path into the `ai-agent` tree, so that move edits config *data*, not just skill prose.
- **No schema validation.** See the rejected option above. The failure it would catch — a dangling `software.<app>.server` — is currently caught by `read-state.py`'s explicit check and by nothing else.
- **`software.json.pre-dokploy` and `software.json.pre-skillmove`** remain in `~/.config/hetzner/`, untracked by chezmoi. Neither backup nor litter has been decided.
- **Two live copies of these skills.** The installed set under `~/.claude/plugins/marketplaces/marketonfire` is a clone of this repo and does **not** track it live — measured mid-migration, the clone still contained five `fleet.json` references while the source was already rewritten. The agent session nonetheless picked up the edited skill descriptions from the source tree, so both locations appear registered. This is why `/plugin update` is a required cutover step and why the old config files must not be deleted before it runs.

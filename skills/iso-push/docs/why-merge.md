# Why every landing is a merge commit

> **The short version.** We want one linear lane and a rule that nothing is ever
> pushed straight to `dev`, `test` or `prod`. On GitHub those two goals are in
> direct conflict, because the only landing method that keeps history intact is
> the one that adds a merge commit. `--merge` is not a compromise we settled for;
> it is the single option that survives both constraints, and it is the only one
> that behaves identically on a private free repo and a public protected one.

This document exists because the decision looks wrong at first glance — "you
chose the option that makes merge commits, when you said you wanted a linear
history" — and the reasoning is easy to lose. Everything below is the argument,
with the trees drawn out.

---

## 1. What we were trying to get

A history where each environment branch is a **prefix** of the one above it, and
every commit exists exactly once:

```diff
@@ the shape we want @@
+ feat/a ──┐
+          ├──> dev ──> test ──> prod
+ feat/b ──┘
```

Two properties matter, and they are separate:

- **One lane.** No parallel copies of the same work sitting on branches that
  never rejoin.
- **Ancestry.** `test` genuinely *descends from* `dev`. Not "contains the same
  changes as" — descends from, by SHA.

Ancestry is the one that pays for itself later. It is what makes
`git merge-base --is-ancestor v0.4.0 origin/prod` a real answer to "did this
release reach production", answerable offline, in constant time, with no tree
comparison and no GitHub account.

---

## 2. What GitHub actually offers

Three buttons, and it matters that there are only three:

| Method | Keeps original SHAs | Target descends from source |
|---|---|---|
| Rebase and merge | no | no |
| Squash and merge | no | no |
| Create a merge commit | **yes** | **yes** |
| Fast-forward | *not offered* | — |

Bitbucket and GitLab both expose `--ff-only` as a merge strategy. GitHub does
not, and never has. That single absence drives the whole decision.

### How to read the diagrams below

Every graph is real `git log --oneline --graph --all` output, generated by
running each strategy against the same three commits on two feature branches.
Nothing is hand-drawn. One character is prepended to each line to colour it:

```diff
@@ legend @@
+ green    survives — original sha, reachable from the branch it is drawn on
- red      orphan — same patch, different sha, on a lane that never rejoins
! orange   a node GitHub created at merge time
# grey     annotation, not part of the graph
  plain    a shell prompt, or a graph row carrying no commit
```

## 3. Rebase and merge — where the parallel lanes came from

"Rebase" sounds like it should produce the cleanest possible line. It does the
opposite here, for a reason that is easy to miss: **rebase does not move a
commit, it copies it.** The copy has a different parent, so it has a different
SHA. The original is left exactly where it was.

For a branch that gets deleted immediately after merging, that is harmless — the
original has no name pointing at it and disappears. `iso-push` never deletes a
branch, and `dev`, `test` and `prod` are permanent by definition. So every rebase
leaves a permanent second copy.

Promote through three rungs and the same patch exists four times:

```diff
@@ Rebase and merge — 2 features, 3 rungs @@
+ * 3213edc (prod) ci: add branch-gate workflow
+ * c8646d9 docs(readme): document the vault
+ * bc02c9d feat: add age-encrypted vault
- | * 15d434e (test) ci: add branch-gate workflow
- | * d690a39 docs(readme): document the vault
- | * 0f1ef2d feat: add age-encrypted vault
  |/
- | * 67e39f5 (dev) ci: add branch-gate workflow
- | * 3a5fc5f docs(readme): document the vault
- | * 0d3ed12 feat: add age-encrypted vault
  |/
- | * 83c476d (feat/a) docs(readme): document the vault
- | * a2086c8 feat: add age-encrypted vault
  |/
- | * 65b7d16 (feat/b) ci: add branch-gate workflow
  |/
+ * 18770c6 chore: base
#
# five lanes. one patch, four shas: bc02c9d 0f1ef2d 0d3ed12 a2086c8
# every |/ is a lane ENDING at base, not joining the branch above it
```

Every red line is a commit that will sit in the repository forever, holding a
patch that already shipped, on a branch that will never merge anywhere. The
`|/` rows are not joins — they run all the way down to `base`. `dev` and `prod`
share nothing but the root commit.

Ask git directly and it is unambiguous:

```diff
@@ ask git directly @@
  $ git merge-base --is-ancestor dev prod && echo yes || echo no
- no

  $ git log --all --oneline --grep='age-encrypted vault'
- bc02c9d feat: add age-encrypted vault
- 0f1ef2d feat: add age-encrypted vault
- 0d3ed12 feat: add age-encrypted vault
- a2086c8 feat: add age-encrypted vault
```

`prod` **contains** the work and does not **descend from** the branch that
produced it. That distinction is the whole document.

Two things break permanently, and neither heals on its own:

- **Every surviving branch points at commits its target will never contain.**
  `git log --graph` shows one lane per branch per rung.
- **`origin/test..origin/dev` keeps listing work that already shipped.** The
  range asks "what does dev have that test lacks", and by SHA the answer is
  *everything*, forever. So the next promotion re-proposes commits that already
  landed, and re-raises every conflict they ever had.

> **Why the copies always get new SHAs.** A commit's id hashes its tree, its
> parents, its author *and its committer* — name and timestamp. Replay a commit
> onto the identical parent with the identical committer and git hands you back
> the byte-identical object; the first attempt to reproduce this graph locally
> collapsed into one clean lane for exactly that reason. GitHub never lets that
> happen: it stamps the committer to the merging user at the merge moment, so
> every replayed commit is a new object by construction. There is no way to
> configure your way out of it.

There is also a quieter failure. `git describe --tags origin/prod` needs the tag
to be *reachable*. Under rebase the tag sits on a commit only `dev` holds, so
`prod` cannot be described at all, and "which release is production on" stops
having a cheap answer.

## 4. Squash and merge — the same wound, plus amnesia

Squash is rebase's problem with the individual commits thrown away as well. One
new SHA replaces N originals, so the copy count is lower but the disconnection is
identical — and now the target cannot even name what it received.

```diff
@@ Squash and merge — same 2 features, same 3 rungs @@
! * 5ea9569 (prod) chore: promote test (#12)
- | * dd42122 (test) chore: promote dev (#11)
  |/
- | * e6e0821 (dev) ci: add branch-gate workflow (#7)
- | * e1c0bfd feat: add age-encrypted vault (#5)
  |/
- | * 83c476d (feat/a) docs(readme): document the vault
- | * a2086c8 feat: add age-encrypted vault
  |/
- | * 65b7d16 (feat/b) ci: add branch-gate workflow
  |/
+ * 18770c6 chore: base
```

Fewer copies than rebase, and the lanes are just as disconnected. But squash adds
a failure the others do not have — ask production what it is running:

```diff
@@ ask production what it is running @@
  $ git log --oneline prod
! 5ea9569 chore: promote test (#12)
+ 18770c6 chore: base
```

**Two commits.** The three commits that actually built the feature are not in
`prod`'s history at all — they were flattened into `#11`, which was flattened
again into `#12`. There is no `git log` that recovers them. The release notes,
the bisect targets, the `git blame` attribution: gone at the first rung and gone
again at the second.

Worth being precise about the trade, because squash is a reasonable default in
many teams: it is genuinely good for a **short-lived branch that is deleted on
merge**, where the intermediate commits are scaffolding nobody will read again.
It is wrong for a **promotion between long-lived branches**, where the commits
are the release notes and the branch outlives the merge. `dev → test → prod` is
entirely the second case.

---

## 5. Create a merge commit — one lane, ancestry intact

The merge commit has two parents. The second parent *is* the source branch tip,
unchanged — same SHA, same author, same date, the exact object CI tested.

```diff
@@ Create a merge commit — same 2 features, same 3 rungs @@
! *   98c1767 (prod) Merge pull request #12 from test
  |\
! | * ec8827d (test) Merge pull request #11 from dev
  |/|
! | *   98b90e8 (dev) Merge pull request #7 from feat/b
  | |\
+ | | * b9e5a80 (feat/b) ci: add branch-gate workflow
  | |/
  |/|
! | * 609acce Merge pull request #5 from feat/a
  |/|
+ | * e03d7bc (feat/a) docs(readme): document the vault
+ | * 698f6b0 feat: add age-encrypted vault
  |/
+ * 5a3b12e chore: base
#
# no red. every |/ JOINS the lane above it instead of running down to base.
# three work commits, three shas, each drawn exactly once.
```

Compare the `|/` rows against the rebase graph: there they terminated lanes at
`base`, here they close them into the branch above. Same characters, opposite
meaning — that is the visual difference between a copy and a join.

Every orange node is structural. Strip them and the green lines are the whole
content of the release, each appearing once:

```diff
@@ strip the structural nodes and the release is all that is left @@
  $ git log --oneline --no-merges prod
+ b9e5a80 ci: add branch-gate workflow
+ e03d7bc docs(readme): document the vault
+ 698f6b0 feat: add age-encrypted vault
+ 5a3b12e chore: base

  $ git merge-base --is-ancestor dev prod && echo yes
+ yes
```

That is the "linear tree" that was actually wanted. Here is the same shape on the
real repository this skill was rebuilt against:

```diff
@@ the same shape on the real repository @@
  $ git log --oneline --graph origin/prod
! *   bd50c0b Merge pull request #12 from IsaiaScope/test
  |\
! | * 1ce27e5 Merge pull request #11 from IsaiaScope/dev
  |/|
! | *   c49fce9 Merge pull request #6 from IsaiaScope/release/v0.1.0
  | |\
+ | | * a3c0752 chore(release): 0.1.0
  | |/
! | * 3d8f641 Merge pull request #5 from IsaiaScope/feat/encrypted-secrets-vault
  |/|
+ | * 0f67d96 ci: add branch-gate workflow and pre-push guard
+ | * b59f042 docs(readme): document the chezmoi source layout and encrypted vault
+ | * 0199b30 feat: add age-encrypted vault for hetzner credentials
  |/
+ * de22bee refactor: clean up .chezmoiignore …
```

Each of the three feature commits appears **once**. `prod` reaches all of them
through the joins. Note the `|/|` rows: those are the promotions, and they close
the lane rather than starting a new one.

A first-parent walk collapses the joins away — but read it carefully, because it
answers a narrower question than it looks like:

```diff
@@ first-parent — what landed ON this branch @@
  $ git log --first-parent --oneline origin/prod
! bd50c0b Merge pull request #12 from IsaiaScope/test
+ de22bee refactor: clean up .chezmoiignore …
```

Exactly one node for the promotion into `prod`. PR #11 (`dev → test`) does *not*
appear, because it is on `test`'s lane — it is the second parent of #12, not the
first. So `--first-parent <branch>` reads "what landed **on this branch**", one
line per landing. To see the promotions into `test`, ask `test`.

## 6. Why the fast-forward we wanted does not exist

A fast-forward would have been perfect: no new commit at all, the branch ref just
slides forward along history that already exists.

And in the cascade it is *always available*, structurally. `test` was branched
from `dev` and receives only `dev`, so `dev` is already a descendant of `test` at
merge time. There is nothing to reconcile:

```diff
@@ before the promotion @@
+ * 83c476d (dev) docs(readme): document the vault
+ * a2086c8 feat: add age-encrypted vault
+ * 18770c6 (test) chore: base
#
# $ git merge-base --is-ancestor test dev && echo yes
# yes — dev is already a descendant. nothing to reconcile.
```

`test` only has to slide up a lane it is already on. `--ff-only` does exactly
that, and creates **no object at all** — the two branches simply name the same
commit:

```diff
@@ git merge --ff-only dev @@
+ * 83c476d (test, dev) docs(readme): document the vault
+ * a2086c8 feat: add age-encrypted vault
+ * 18770c6 chore: base
```

What GitHub does instead, with no way to ask for the above:

```diff
@@ gh pr merge --merge @@
! *   9971193 (test) Merge pull request #11 from dev
  |\
+ | * 83c476d (dev) docs(readme): document the vault
+ | * a2086c8 feat: add age-encrypted vault
  |/
+ * 18770c6 chore: base
```

One extra node. Note what it is *not*: nothing turned red. The fast-forward is
strictly tidier, and it is the only one of the three that is unavailable.

Fast-forward is reachable exactly one way:

```bash
git push origin dev:refs/heads/test    # a plain, non-force push
```

Which is precisely the thing the no-direct-push rule forbids. So on GitHub:

> **Linear history and no-direct-push are mutually exclusive.** You may have
> either. You may not have both.

We keep no-direct-push. Which forces PR landings. Which leaves three methods.
Two of them rewrite. **One remains.**

## 7. Why the no-direct-push rule stays

This is the constraint that decided it, so it deserves its own justification.

The rule has to hold on repos where GitHub cannot enforce it:

| Repo | Plan | Protection API | Enforced by |
|---|---|---|---|
| private | Free | `403` | our pre-push hook |
| private | Pro / Team | available | GitHub |
| public | any | available | GitHub |

On a **private repo on the free plan**, `PUT /repos/:owner/:repo/branches/:b/protection`
returns `403`. There is no server-side gate at all. The pre-push hook
`iso-init-repo` installs is the only thing that refuses, and a client-side hook
is a guardrail against habit, not a control — a fresh clone has not run
`git config core.hooksPath .githooks`, and the web UI never sees it.

That has one consequence that settles the design:

- If the hook is a **blanket ban**, it is simple, has no escape hatch, and is
  correct on every repo. Nothing legitimate ever pushes to a protected branch,
  because every landing goes through GitHub.
- If we allowed fast-forward pushes for promotions, the hook would need to
  distinguish a legitimate cascade push from an ordinary mistake — by shape, at
  push time, in bash. And the same flow would then behave *differently* on a
  public repo, where GitHub rejects the push outright.

One rule, one flow, every repo. A workflow that only works while you are on the
free plan, or only while the repo is private, is a workflow that breaks on the
day you change either — and it breaks during a release, which is the worst
possible moment to discover it.

---

## 8. What it costs

One empty commit per landing. Worth stating precisely, because "merge commits
pollute history" is usually said about a different situation:

- The count grows with **landings**, not with **commits**. A promotion carrying
  40 commits adds *one* node. Under rebase it would have added 40 duplicates.
- The node carries no content. `git log --no-merges` never shows it; `git log
  --first-parent` shows only it.
- `git blame` is unaffected — a merge commit introduces no lines.

The usual complaint about merge commits comes from `main`-with-many-contributors,
where dozens of small merges interleave into a braid. A cascade is **serial** by
construction: one promotion at a time, in a fixed order. The braid cannot form.

## 9. What we get back

| Question | Command |
|---|---|
| which release is `prod` on | `git describe --tags origin/prod` |
| did 0.4.0 reach `prod` | `git merge-base --is-ancestor v0.4.0 origin/prod` |
| what has landed since | `git log --oneline v0.4.0..origin/dev` |
| one line per landing on a branch | `git log --first-parent origin/<branch>` |

Every one of these is a graph query — constant work, offline, exact. Under rebase
merge none of them worked, because each rung held its own copy of everything and
the tag matched none of them. Answering the same questions meant comparing trees.

## 10. The guardrail

The whole model rests on one repo setting — *Allow merge commits* — that someone
can change in the web UI without telling anyone. So `push.sh integrate` does not
trust it. After every landing it asserts the property it actually depends on:

```bash
git merge-base --is-ancestor "origin/$src" "origin/$dst" \
  || die "'$src' is not an ancestor of '$dst' after PR #$pr — the merge rewrote history"
```

If the repo's method is flipped to rebase or squash, the **next promotion fails
loudly** instead of quietly duplicating history and being discovered three
releases later.

Two related traps the same code guards:

- **GitHub marks a PR merged by reachability, not by button click.** Push
  something that makes the head reachable from the base and the PR flips to
  Merged — regardless of failing checks, and irreversibly. So `integrate`
  verifies the base actually moved, rather than trusting the PR state.
- **A non-merge commit on `test` or `prod` that `dev` lacks** is a hotfix applied
  straight downstream. `assert_no_own_work` refuses to promote over it, and uses
  `git cherry` to tell a genuine hotfix apart from leftover rebase duplicates —
  because the advice differs completely: carry the hotfix down, discard the
  duplicates.

---

## Summary

| Constraint | Consequence |
|---|---|
| No direct push to protected branches | every landing is a PR |
| GitHub offers no fast-forward merge | three methods remain |
| Branches are never deleted | rebase/squash copies are permanent |
| Ancestry must hold by SHA | rewriting is disqualified |
| → | **`gh pr merge --merge`, always** |

Rebase is safe only for a branch that dies. Nothing here dies. So nothing here
rebases.
